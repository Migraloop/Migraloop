# Multi-Pipeline throughput evidence and Capacity Estimate

Post–basic-complete performance work measures **end-to-end Managed Delivery** rate on a Deployment-realistic **mega-mix** Lab Scenario that covers every shipped path family (multiple Direct Pipelines across tables plus Transform Pipelines for `$project`/field ops, `$match`, `$lookup`, `$unionWith`, `$unwind`, `$group`, and distinct/`$addToSet`). Absolute floors are path aggregates under Incremental Capture: Direct paths combined ≥ 100k e2e QPS and Transform paths combined ≥ 50k e2e QPS—hard gates and intended low bars; the program must keep applying correctness-preserving techniques until a written means-exhaustion list shows remaining high-leverage ideas are profile-disproved, correctness-forbidden, or clearly poor ROI.

Multi-Pipeline proof is dual-gated: aggregate scaling `QPS_mix ≥ 0.7 × Σ QPS_solo_i`, and per-Pipeline degradation `QPS_mix_i ≥ 0.95 × QPS_solo_i`. Evidence counts only when Source, Platform Store, and Target are **not** saturated; Local Sync Lab Fixture sizing must be raised until that holds. The product must not mutate user Source/Target database configuration; instead it exposes a **Capacity Estimate** (limiting component + coarse max e2e QPS) via Operator command in live Deployments, with the same component-stat semantics in Lab Scenario reports (`infra-saturated` means re-size and re-run, not “product failed”). Architecture may introduce any component (e.g. cache/memory layers, parallel Affect, batching) if Change Ordering, Eventual Consistency, and ADR-0029 hold. Initial Load has a separate bar: `IL_rate ≥ 0.5 ×` same-shape Direct Incremental e2e rate—not the CDC absolute floors.

**Rejected alternatives:** (1) single-Pipeline microbench as the headline accept—misses contention; (2) aggregate-only success without per-Pipeline degradation—hides starvation; (3) counting DB-saturated runs as product ceiling; (4) auto-changing customer Oracle/Mongo settings; (5) Direct-only performance programs (forbidden by ADR-0029).
